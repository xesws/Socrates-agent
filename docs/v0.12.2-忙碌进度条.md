# v0.12.2 — 忙碌进度条

> 读者：「你之前做的那个动画效果做到哪儿去了？我怎么没看到呢？」
> 又：「别用气泡啊，别用气泡。模仿 Kimi Code CLI 那个进度条一样的东西。」
> 日期：2026-08-21。

## 先说清楚：v0.12.0 根本没做动画

当时给的是两条路，读者选了「真流式」，所以做的是**状态行里的活体计数**
（`苏格拉底在想… 3.6k 字`）。机制是通的——实测 `think` 事件穿过了 SSE，
产物里也有处理分支。

**但我把信号放错地方了。** 唯一的提示是侧栏最底下那行 10px 小字，
而读者的眼睛在那个空气泡上。技术上对，实际上等于看不见。

## 走过的一次弯路

第一版把指示器画进了气泡里（三个跳动的点 + 字数）。读者当场否掉：
「别用气泡。」已撤。

## 这一版

底座里横一条**不确定型**进度条，在状态行上面：

```
[ 引用 ]
[ 芯片 ]
▬▬▬▬▬▬▬▬▬▬  ← 一条亮块来回穿，忙就亮
上下文 12.4k · 回复 0.8k · 本会话 128k
[ 用当前选区 ][ 自己问一句… ][ 问 ]
```

**为什么是不确定型**：我们不知道模型还要写多久，画一条会走到头的假进度就是
在骗人。它只回答一件事——还在动。真实的数字在下面那行状态行里
（推理字数是真从流里数出来的，它不跳就是真卡住了）。

`busy` 为真就亮，一条规则，不用分推理/翻书/吐字三个阶段。

## 减少动态效果时**不整条藏掉**

`prefers-reduced-motion` 下关掉穿梭动画，但把它填满留在那儿——
它是「还在动」唯一的视觉信号，整条填满比一片空白诚实。

## 一个当场被抓的空转看门狗

第一版的 check-css 断言写的是 `css.includes(".sp-bar-fill")`。
把主规则整块删掉之后它**照样绿**——因为 `reduced-motion` 块里还留着一处
同名选择器。改成只查 `reduced-motion` 之前那一段里的完整规则，
再删就真会红了。

## 已知的局限

前端没有 DOM 测试框架，`is-off` 那条开关只有真跑才看得出来。
CSS 那两条由 check-css 守着（删掉主规则会红）。
