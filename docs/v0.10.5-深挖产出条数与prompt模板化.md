# v0.10.5 — 深挖产出条数，以及 prompt 跟着旋钮变

> 读者拍板：「都做，prompt 跟着变。」日期：2026-08-20。

## 为什么这一版比看上去贵一倍

三个硬编码数字**同时写死在给模型的 prompt 里**：

| 数字 | 代码 | prompt 里的同一个数 |
| --- | --- | --- |
| `PROBE_MAX_READS=2` | 解析截断 + 执行截断 | 「就在 need_read 里写行区间，**最多两段**」 |
| 解析上限 `3` | `[:3]` | 「只输出一个 JSON 对象…**最多 3 条**，宁缺毋滥」 |
| `open_used >= 1` | 收割时的计数 | 「这种题**每次最多一条**」 |

只改代码不改 prompt，正好撞上 `config.py` 里自己写下的那条禁令的**镜像版**：
不是「摆一个常量而代码不读它」，而是**代码读了、模型没被告知**。读者把
「每次产出」调到 4，模型仍然只吐 3 条。

所以 `PROBE_SYSTEM` 要模板化。**用 `str.replace()` 不用 `str.format`**：
正文里那段 JSON 模板全是字面 `{` `}`，`format` 会当场炸。

占位符 `«READS»` / `«OPEN»` / `«PARSE»`，中文数词走一张映射表（「最多**两**段」）。
**默认档下渲染出的字符串必须与 v0.10.4 逐字节相同**，配一条测试钉死。

前缀缓存不会失效：同一份设置下 system 仍然逐字节稳定，只是不同设置的读者
各占一份缓存。

## 两个数，一个旋钮

它们不是同一个东西：

- **解析上限**（`probe_parse_cap`）＝ 模型最多能提几条候选；
- **入池上限**（`probe_keep_per_run`）＝ 过完全部校验之后最多存几条。

中间是一个损耗极大的漏斗（depth<4 丢、`validate_slots` 丢、`clean_candidates`
丢、相似度 0.72 丢）。所以两个数必须都在，但**只暴露入池那个**。

解析上限由代码推导：`parse = max(3, keep + 1)`。默认档 keep=2 时 `max(3, 3) = 3`，
一个字节不变。

暴露解析上限的坏处很具体：读者调大它 = 让模型多吐几条废题 = 多花输出 token
而入池数不变，纯亏。

## `probe_open_per_run` 命名但不暴露

它不是预算，是**诚实策略**——open 题 = 手册里没有出处、凭模型记忆答、
答的时候要在开头挑明。默认 keep=2 时允许 2 条 open，意味着整整一轮的深挖
可以全是无出处的。**这条产品承诺不该做成旋钮让读者自己调没。**

做法：给它一个名字（不再是一个匿名的 `1`），`merge_limits` 里夹到 `≤ keep`，
不进设置页。将来要开放时只差一个 UI 项。

## 一句必须写进设置项说明的诚实话

`MAX_RELEASE_PER_TURN = 1` 封顶了整条链路：**不管一次深挖存下几条，每轮
只放出 1 条**，攒过 6 轮（`ITEM_TTL_TURNS`）就丢。

所以「每次深挖最多存几条」调到 5，主要是在增大 `dropped` 堆，不是增大读者
看到的量。不写这句，读者调完会认为功能坏了。
