# v0.10.8 — 上限的三个真 bug（自查 + 两路审查扭出来的）

> v0.10.6 交付之后，一次真跑加两路独立审查扭出三个真问题。
> 日期：2026-08-21。

## ①【最严重】`turn_spend` 从来不清零 —— 「每轮上限」其实是「整场一次性预算」

`session.turn_spend` 只在 `tutor._agent_loop` 里被 `merge` 进去，**全仓没有
任何地方把它清零**。字段注释写的是「本轮主对话已花」，实际行为是终身累加。

三个下游全部中招：

- `max_tokens_chat` 的判据读的就是它 → 上限变成会话终身的；
- `ctx["turn_tokens"]` 从它取 → `max_tokens_cross_book` 也变成终身的；
- SSE `spend.turn` → 状态行上那个「本轮 X」显示的是会话累计，是错的。

实测（cap=5000，每枪 1100）：

```
第 1 轮：带 tools 打了 4 枪，累计 5500
第 2 轮：带 tools 打了 0 枪，累计 6600
第 3 轮：带 tools 打了 0 枪，累计 7700
```

读者的实际体验：填了个「每轮 30k」，第一轮正常，**从第二轮起师傅永远不再翻
手册**，而且 `turn_spend` 会落盘，重启 sidecar 也救不回来，只能新开会话。

**修**：在 `stream_chat`（新一轮的入口）开头清零。**绝不能放进 `_agent_loop`
或 `resume_chat`**——那是同一轮的后半段，清了就等于审批让预算翻倍，
而 v0.10.3 刚刚修过反向的同一件事。

**为什么没抓到**：v0.10.6 的全部五条上限测试**都只跑一轮**。凡是「每轮重置」
型的状态，这个测试形状按定义看不见。本版补多轮测试。

## ②「执行工具批次之前」也要判 —— 实测超出 2.18×，不是文档写的 1.4×

真跑（cap=8000，真模型真手册）：

```
第 1 枪            5697
模型一次批量发了 7 个 read_file，全部执行
第 2 轮顶部撞线 → 收口
收口枪            11761   ← 面对的是多了 7 段正文的 messages
合计              17458 = 2.18 × cap
```

我在 v0.10.6 的文档里推的 1.4× 假设「每轮一个工具调用」。**真实模型一次发
一批。** 余量取的是「上一枪的 prompt_tokens」，而收口枪面对的 messages 里多了
整整一批工具结果——两者之间隔着一次批量执行。

**修**：在 `_run_tool_batch` 之前用同一个判据再判一次；撞线就**不执行这一批**，
直接收口。收口枪于是只面对没有那批正文的 messages，按实测数验算 2.18× → 约 1.55×。

**但文案里不能写任何固定倍数。** 推一遍就明白：进入第 k 枪前必有
`S_{k-1} + P_{k-1} < cap`，所以 `S_{k-1} < cap`；之后至多再打两枪，于是

> **上界 = cap + 2·(单枪最大输入 + 单枪最大输出)，与 cap 无关。**

cap 越小倍率越大，理论上无界（实测把 cap 填成 1 时倍率是六位数）。而放大器有
三个且都没闸：`_run_tool_batch` 对模型一枪吐多少个 `tool_calls` 没有上限、
读**当前手册**完全不计跨书预算（那是 `config.py` 明文的豁免）、单次读取封顶
5000 字符 × N 次。所以诚实的说法是「超出量大致等于一次收口回答的开销，
取决于这一轮已经翻了多少东西」，而不是任何一个比例。

⚠️ **协议约束**：OpenAI 要求每个 `tool_call` 都有配对的 `tool` 结果消息，
少一条供应商直接 400。所以不执行也要给这一批每个调用补一条合成结果
（「本轮额度用完了，这次没有执行」）——顺带把「为什么没读到」告诉了模型。

**文档和设置页文案里那个倍数要一起改**：假装是 1.4×，读者第一次看到 2 倍
就再也不信这个功能了。而换成 1.55× 同样不诚实——按上面那个公式，
它压根不是一个比例。

## ④ `merge_limits` 会抛 `OverflowError`，破掉「只夹紧不报错」的承诺

`float(got)` 只挡了 `(TypeError, ValueError)`，而 JSON 允许任意精度整数，
`float(10**400)` 抛的是 `OverflowError`。读者拿到的是「对话中途出了意外错误」
——正是请求体用 dict 而不是子模型时承诺要避免的那个形状。

插件自己发不出（前端先归一化过），但第三方客户端和手写 curl 能。

## ③ 跨书的第三道闸在审批续跑的 `rest` 批次里完全失效

v0.10.3 专门修过「一轮对话不再拿两份跨书预算」，把 `cross_book_chars/reads`
冻进 `session.pending` 并在续跑时恢复。但 v0.10.6 新加的第三道闸读的是
`ctx["turn_tokens"]`，而 `resume_chat` **只恢复了前两个**。

于是续跑那半轮里 `ctx.get("turn_tokens")` 是 `None` → `over(0, cap)` 恒假 →
第三道闸整段失效，直到跑完一枪之后才补上。

**修**：`resume_chat` 建完 ctx 之后把 `turn_tokens` 一起种回去。
这条和 ① 是同一处语义的两半：①管「什么时候清」，③管「什么时候续」。

## ⑤ 加完 ② 之后，循环顶部那道判的余量变成了死表达式

这是变异检查逼出来的：修完 ② 之后，「循环顶部要留余量」那条变异体**空转**了
——把余量改成 0，测试照样绿。

推一遍就明白：工具执行既不改 `turn_spend` 也不改 `usage`，所以
**本轮 k 的顶部和上一轮 k-1 的批次前，输入完全相同**。批次前那道过了，
顶部那道必过。余量写在顶部是一个永远不会先触发的表达式。

它真正起作用的只有一种情况：**审批续跑**。那时 `turn_spend` 是从暂停前带
过来的，而 `usage` 刚重置成 0（没有上一枪可估），判据就该是裸的
「已经花超了就别再开工具枪」。

**处理方式**：不是给它补一条假测试盖住，是**把那个死余量删掉**，
并给它补一条只在续跑场景下才会红的测试。两道判于是各有各的活：

| 判据 | 什么时候起作用 | 留不留余量 |
| --- | --- | --- |
| 循环顶部 | 只有审批续跑（`usage` 刚归零） | 不留——没有上一枪可估 |
| 执行批次前 | 每一轮 | 留，取上一枪的 `prompt_tokens` |
