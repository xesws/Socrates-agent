# v0.10.4 — 深挖频率（复活一个死字段）

> 读者要配「深挖频率」。日期：2026-08-20。

## 现状：没有轮次冷却，而且有个字段白存了

`should_probe` 里所有闸门都是失控保护或语义排除，**没有一条是降频手段**——
这是读者当初自己选的「每轮实质回复都探」。

而 `SessionLedger.last_probe_round` 这个字段**存在、落盘、被 `try_claim` 写入，
但全仓从来没有被读来做过任何判断**（grep 核实）。它就是给这件事预留的位置。

## 语义

`probe_every_n_rounds` = 两次深挖之间至少隔几轮。**0 = 每轮实质回复都探**，
也就是今天的行为。默认 0，所以本版对不改设置的读者零影响。

## 判定放 `should_probe`，写留在 `try_claim`

- `should_probe` 是纯函数、零成本、**带具名理由**，而且已经有一张参数化的
  理由表当文档。所有「别花这个钱」的规则都在那儿，这条也是。
- `try_claim` 持锁，看起来能避免竞态——但 `/v1/chat` 全程持会话锁，同一会话
  两个请求不可能并发走到这里，原子性不是需求。而且 `try_claim` 只能返回
  `None`，读者永远分不清是配额满了还是在冷却。
- 写留在 `try_claim` 不动。**写在持锁处、读在纯函数处**，职责正好。

新理由字符串 `cooldown`，排在 `cover-or-appendix` 之后、`budget` 之前——
「探得太密」比「配额用完」更具体，该先听到。

## 一个非写不可的短路

```python
if lim.probe_every_n_rounds and now_round - last_probe_round <= lim.probe_every_n_rounds:
   ^^^^^^^^^^^^^^^^^^^^^^^^^^^^ 这一半不能省
```

一轮出错时 `app.py` 的 finally **不给 `sess.turns` 加一**。于是「上一轮失败 +
这一轮成功」会出现 `now_round == last_probe_round`。写成裸的 `<= 0` 时，
**N=0 也会在这种会话里开始拦**——那就不是「和今天一样」了，而且极难复现。

配一条专门的边界测试钉住它。

## 三个新参数全部带默认值

所以 `test_probe.py` 那张 `_BASE` 参数表一个字符都不用改。
