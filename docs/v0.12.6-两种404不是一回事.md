# v0.12.6 — 两种 404 不是一回事

> v0.12.3–v0.12.5 三版落地之后过了一轮审查。7 条里 6 条属实，
> **第 1 条是那三版自己引入的真回归**。这一版把它们全修掉。
> 日期：2026-08-21。

## ① 会话没了，和笔记被改名，不是同一种 404

这是这一版最要紧的一条，也是我自己写坏的。

v0.12.4 给 `deeppoll` / `send()` / `doApprove()` 加 404 兜底时，判据写的是
**「状态码是 404 就当成会话被归档了」**。但 `pen/app.py:159` 的 `_meta_or_404`
对**「笔记被重命名或移走」**也抛 404——那是读者在 Obsidian 里的日常操作，
而那条 detail 里有唯一能救他的一句「原文找不到了，请重新框选一次」。

于是读者改个笔记名之后看到的是：

> 这场对话超过保留期，已归档，而且新会话没开起来（sidecar 连不上？）。

**真正该说的那句被吞掉了**，换上来的这句里只有「新会话没开起来」是真的
——而它之所以真，恰恰是因为重开新会话走的 `POST /v1/sessions` 第一件事
**还是** `_meta_or_404`，撞的是同一个改名 404。sidecar 好好跑着。
拿一个 bug 换了个更难受的。

（这段初稿引的是另一条文案「……刚才那句已经重新问出去了」。那条在这个
场景下**根本走不到**：`reviveSession()` 必然也失败，`this.err` 先被
`errSessionArchivedHard` 填满，后面那句 `if (!this.err)` 永远盖不上去。
本节自己犯了它正在声讨的毛病——描述一条没验证过的路径。已改。）

修法是让服务端**明说是哪一种**。「这场会话没了」那一种，detail 从一句字符串
变成 `{"code": "session_gone", "message": ...}`：

```python
def _no_session(lang: str) -> HTTPException:
    return HTTPException(404, {"code": "session_gone", "message": msg("session.unknown", lang)})
```

`pen/app.py` 里 7 处「会话查不到」全部走它，其余三种 404
（手册未登记、笔记被改名、提案已失效——共 4 个 raise 点，提案那种占两处）
照旧是字符串。前端
`isGone()` 于是从「状态码 404」收紧成「404 **且** code 是 `session_gone`」。

**为什么走 body 里的 code 而不是响应头**：自定义响应头要 CORS `expose_headers`
才读得到，而 `detail` 这条路 `api.ts` 本来就在解析，一处改完所有调用方都认。

**两处出错点必须同源**：`j()` 和 `readSse()` 各有一份错误解析，v0.12.4 时是
两段几乎一样的代码——这仓库反复栽的「两个闸不同源」。合并成一个 `errorFrom(res)`，
`check-api.mjs` 里那两条 `streamChat/streamApprove 的 404 也拆得出 code`
就是守这个的。

## ② `pending` 那条豁免是无界的

v0.12.4 的规则表里第三行写的是「挂着 `pending` 的 → **永不删**」。
听起来保守，实际是一条**谁都清不掉**的豁免：任何带 `pending.id` 的文件
从此永久占盘，清理跑一万遍也动不了它。

实测真实 `.pen`（2026-08-21 当天，3219 个会话文件）里，
**551 个是「pending + messages == 1」**——全是测试污染留下的假数据
（id 只有三种：`pend1` 225 个、`pend2` 225 个、`pid1` 83 个），而按第一版规则它们一个都删不掉。
一条号称有上限的清理规则，**17%** 的文件豁免在外。

改完之后干跑（不删文件，只问 `_keep_seconds` 每个文件该留多久）：
**落在「永不删」里的从 551 个变成 0 个**。

而**真实的 pending 不可能长在空会话上**：`pen/tutor.py:701` 设 pending 之前，
这一轮的 user 消息和带 `tool_calls` 的 assistant 消息早就 append 进
`session.messages` 了（`tutor.py:544`），最少 3 条。所以「空 + pending」
只可能是假数据或坏文件。

判断顺序改成**先判空**：

| 类型 | 判据 | 保留 |
| --- | --- | --- |
| 空会话（含「空 + pending」） | `len(messages) <= 1` | 1 天 |
| 聊过 + 挂着 pending | | 永不删 → **30 天**（见文末【5】） |
| 聊过的 | 其余 | 7 天 |

两条测试守着两边：`immortality` 那条证明假 pending 会被扫掉，
`real_pending_still_survives` 那条证明真 pending 照旧免死。

## ③ `captureSelection` 里那个裸 catch

`PenView.ts` 划词时若笔记已绑过会话，会先 `getSession(bind.session_id)`，
而那个 `catch` 是**裸的**：

```ts
try { sess = await this.api().getSession(bind.session_id); }
catch { sess = await this.api().createSession(hid); }   // ← 任何错都走这
```

一次网络抖动、一个 500、笔记改名那种 404，全都会**静默**开一场新会话并把
笔记重新绑上去。旧那场其实还在盘上，但 `bindNote` 一改就再也没人指得到它了
——不可逆，而且读者一个字的提示都收不到。

会话按时间清理上线之后，这里是读者**最可能**撞到「会话没了」的地方
（划词是入口，`send()` 是之后的事）。改成只认 `isGone(e)`，其余原样往上抛；
真换了就 `new Notice(t().noticeSessionRenewed)` 说一声。

## ④ 三条文案在断言自己并不知道的因由

`errApprovalArchived` 原文是「这次编辑**等太久**，所在的会话已**过保留期归档**了」。
可 `retention.py` 恰恰**永不删**挂着真 pending 的会话——这条文案描述的因果
在自己的代码里不可能发生。读者照着它去等、去查保留期，白费一趟。

三条全部改成只说**发生了什么**，不说**为什么**：

> 这次编辑所在的会话在 sidecar 上已经找不到了。原文没有被改动。已经给你开了新的一场，重新问一次就行。

「多半是过了保留期被清理」作为**猜测**保留在另外两条里，措辞上和事实分开。

## ⑤ 好消息不该画成红色错误条

`send()` 重发成功之后那句「已经给你开了新的一场，刚才那句已经重新问出去了」
走的是 `this.err`，而 `this.err` 在 `paintBar` 里渲染成错误条。**一切都办妥了，
界面上却像出了事。** 改走 `new Notice(...)`，键名也从 `errSessionArchived`
改成 `noticeSessionArchived`——名字和去处对上，下次不会有人再顺手塞回 `err`。

`errSessionArchivedHard`（连新会话都没开起来）留在 `err` 里，那是真的错。

## ⑥ 内存那个数我算错了 3 倍

v0.12.5 文档和 `config.py` 注释里写的「19 条 messages / 59539 字符 ≈ 116 KB，
32 场约 3 MB」是按 **2 字节/字符**估的（59539 × 2 = 116.3 KB，正好对上），
既漏了 Python 每个 str/dict 对象的头，也低估了中文在 UTF-8 里的三字节。

递归 `sys.getsizeof` 重量真实 `.pen` 里最大的那场：24 条 messages /
66817 字符 → **364 KB**，32 场 ≈ **11.4 MB**。

**上限 32 不改**：11.4 MB 是最坏情形（那是全仓最大的一场），真实平均一场只有几 KB。
`docs/v0.12.5-内存淘汰.md` 里加了一条更正块，原文保留——那份文档是历史记录。

## ⑦ `POST /v1/maintenance/purge` 的暴露面，说清楚

它是个**无参数、无鉴权的 simple request**：`Content-Type: application/json`
会触发预检，但任何网页都能用 `text/plain` 的表单式 POST 绕过预检打到
`127.0.0.1:8765`。所以要诚实地写下它能干什么：

- **只能触发一次清理**，删的是**已经过期**的会话——和 sidecar 每次启动
  自己跑的那次**完全一样**，没有多删一个文件的能力
- 不接受任何参数：改不了保留天数、指定不了 sid、换不了目录
- 删一个会话时**会连带删掉它的深挖账本** `.pen/probes/<sid>.json`
  ——按**会话**索引的那一个。按**手册**索引的 `.pen/probes/<hid>/quota.json`
  （每小时成本闸门）不碰，`mutate.py` 里有一条突变守着这个分界
- 不碰快照、不碰轨迹、不碰写回提案

**打击面 = 把一次本来就会发生的清理提前**。这个仓库整体是「只监听本地、
数据不出 `.pen`」的形状，没有为它单独引一套鉴权；但把它记在这里，
以后要是给这个端点加参数（比如「立刻清空全部会话」），这段话就是那道闸。

# 第二轮：另一个审查 Agent 的 5 条

第一轮的 `reviewer-correctness` 迟到了一步，交上来的是对 v0.12.3–v0.12.5 的
审查。它报的 5 条里，第 1 条（isGone 语义）正是上面 ① 已经修掉的那一条；
另外 4 条是新的，一并修在这一版里。

## 【2】`propose` 的尾段是裸奔的——锁会永久泄漏

`pen/app.py` 的 `/v1/writeback/propose` 有三段各自的 `_save_and_unlock`，
但从 `old = path.read_text(...)` 到最后那次 `_save_and_unlock` 之间
**完全没有异常保护**。`render_new_text` / `unified_diff` / `_content_fp`
任何一处抛出（笔记在这中间被移走、被同步工具换成非 UTF-8），
`lock.release()` 就不执行。

后果：**这一场对读者是永久 409「这场对话还在跑」**，重启 sidecar 之前解不开。
而 v0.12.5 的「绝不淘汰持锁会话」还把它放大了——一个泄漏的锁 = 一个永远
出不了 `_items` 的会话，对 `MAX_LIVE_SESSIONS` 完全豁免。卡住 N 场，
`_items` 就无视上限长到 N。**我上一版治内存泄漏，自己的兜底路径又造了一个源头。**

改成**一个 `try/finally` 罩住全部**，三段重复的 `_save_and_unlock` 全删。
新测试断言的是读者看得见的那个东西：尾段炸过之后再打一次，**不许是 409**。

## 【3】「钉回实例」只关掉了一半

v0.12.5 的 commit message 说修了「一整轮对话凭空消失」。查下来只修了一半。

`try_lock` 把手里的实例钉回 `_items`，保证的是「抢到锁之后表里是我这个」，
**没保证我这个是最新的**。生产次序是 `get()` → `_meta_or_404` / `load_index`
（真磁盘 I/O，毫秒级）→ `try_lock()`：

```
T1 get(S) 拿到 X → 淘汰把 X 扫出表 → T2 get(S) 从盘上重建 Y，
锁上、跑完一整轮、save(Y)、放锁 → T1 这才 try_lock(X)，锁是空的，
抢到，还把陈旧的 X 钉回表里 → 收尾 save(X) 把 T2 那一轮整个盖掉。
```

`try_lock` 现在返回 `(锁, 当家实例)`，抢到锁之后认表里那个；表里也没有就
**回盘上现读**——此刻锁在我们手上，谁也不能再改这一场，磁盘那份就是权威。
`_try_lock_session` 跟着返回两个值，三个端点全部改成 `lock, sess = ...`。

触发要 ≥32 场并发持锁，单读者的 Obsidian 插件基本到不了，但「说修了其实
只修了一半」比没修更糟。三条新测试分别守：认表里的、回盘上读的、
盘上也没了（保留期清理插在中间）时用手上这个别甩 404。

## 【4】重发那个窗口里 UI 是解锁的

`send()` 的 `finally` 先把 `this.busy = false` 并重画（输入框和发送键当场
可用），之后才 `await this.reviveSession()`（一次 HTTP 往返）。读者在这个
窗口里再按一次回车，第二个 `send()` 用的还是**旧的死 sid**（`adopt()` 还没跑）
→ 又一个 404 → 又一次 revive：建出两场会话、`bindNote` 打两次、
**同一句话被计费发两遍**，`this.msgs` 被两次 `adopt()` 互相清空。

`gone` 为真时 `finally` 里不放下 busy，等 revive + 重发走完再放；
revive 失败那条路自己收干净。

## 【5】`pending` 那条豁免仍然没有天花板

上面 ② 只砍掉了「空 + pending」。**真** pending 那一档还是 `inf`：读者在
审批面板开着的时候关掉 Obsidian、之后点「新开会话」，那一场就再也没人碰它，
永久占盘。一条没有天花板的豁免就是一条谁都清不掉的泄漏——正是这次要治的病。

加 `SESSION_KEEP_DAYS_PENDING = 30`。30 天足够任何人回来点那一下，
而 `retention.py` 里现在**一个 `inf` 都没有了**。

## 三条弱断言，一并收掉

审查还点出三处「不算空转但守不住东西」的地方：

1. `test_purge_is_silent_when_there_is_nothing_there` 里那句
   `assert not config.PEN_DIR.exists()` 在隔离 fixture 下**恒为真**，
   而 `sessions_dir()` 自己会 `mkdir(exist_ok=True)`——所以 `purge` 里那个
   `except OSError` **一次都没被跑到**，docstring 声称的「目录不存在不该让
   sidecar 起不来」根本没被守住。补一条：把 `.pen` 那个位置塞成**文件**，
   `mkdir` 抛 `NotADirectoryError`，这才真踩到那个分支。
2. `test_touch_on_a_missing_session_is_silent` **一个断言都没有**
   （注释自己写着「不抛就算过」）。真正要守的是 `Path.touch()` 默认会
   **create**——少了那道 `is_file()`，会话目录里会凭空长出空文件。改成断言这个。
3. `retention.touch` 的 docstring 点名 `GET /deep`、`retarget`、`apply`
   三条端点，读起来像是它们也调了 `touch()`——**并没有**。改成说实话：
   只有两处调，那三条被上游兜住了。
