# v0.12.5 — 内存淘汰

> 读者：「我需要你去设计一个内存更新的机制，不然用户用插件的时候，
> 迟早会把自己的电脑搞爆。」
> 日期：2026-08-21。

v0.12.4 管的是**磁盘**。这一版管**内存**——`SessionStore` 此前完全没有淘汰：
`_items` 和 `_locks` 都是纯 append 的普通 dict，而 sidecar 是常驻进程，
读者一天划几百次词就是几百个 `PenSession` 外加几百把 `Lock` 永远挂着。

## 上限 32 场

按实测最坏那场估：19 条 messages / 59539 字符 ≈ 116 KB，**32 场约 3 MB**。

> **更正（v0.12.6）**：上面这个数错了，差 3 倍多。它按的是 **2 字节/字符**
> （59539 × 2 = 116.3 KB，正好对上），既漏了 Python 每个 str/dict 对象的头，
> 也低估了中文在 UTF-8 里的三字节。重新用递归 `sys.getsizeof` 量真实 `.pen` 里最大的那场：
> 24 条 messages / 66817 字符 → **364 KB**，**32 场约 11.4 MB**。
> 上限 32 不改——11.4 MB 是最坏情形，真实平均一场只有几 KB。
淘汰只是把它从内存里放掉，**磁盘上的快照一个字没动**，下次 `get()` 现读回来。

`_locks` 和 `_items` **一起**淘汰。只淘 `_items` 会留下 `_locks` 这条更小
但同样无界的泄漏——每个 session id 一把 Lock，永不回收。

## 两条不变量

### ① 绝不碰 `lock.locked()` 为真的那场

`/v1/chat`、`/approve`、`/propose` 三处都是先 `STORE.get()` 拿到 `sess` 引用，
再长时间持锁改它。把 `_items[sid]` 踢掉之后，别的请求 `STORE.get(sid)` 会从
磁盘**重建出第二个实例**，而收尾的 `STORE.save(sess)` 又拿第一个实例覆盖回去
——表现就是「对话中途重开侧栏，上一条回复消失」。

读者拍板的取舍：**宁可暂时超上限**。在跑的比上限还多时 `_items` 就真的超出去，
锁一放，下一次淘汰再把它收回去（有一条专门的测试盯着这个「暂时」，
不然「绝不碰正在跑的」会变成永久豁免，泄漏照旧）。

### ② 淘汰必须自己上锁

`_lock_meta` 原来**只护 `_locks`**，`_items` 的读写完全裸奔。
单次 getitem/setitem 在 GIL 下是原子的，所以以前不炸；但淘汰是
「查长度 → 挑最旧 → pop」这种 read-modify-write，不整体加锁会踩空 `KeyError`。
FastAPI 的 `def` 端点跑在 40 线程的 threadpool 上，这不是理论问题。

现在 `_meta`（改成 `RLock`）同时护两个字典。磁盘 I/O 一律放在锁外——
它是每个请求都要过的窄门，别把读写盘关在里面。

## 写这一版时才发现的两个坑

**`try_lock` 的参数必须是 `PenSession`，不能是 `session_id`。**
第一版写成 `lock_for()` + `acquire(False)` 两步，中间那条缝里淘汰能挤进来
把 `_locks[sid]` 换掉，两个线程各拿一把不同的锁进临界区。改成一个方法之后
仍然不够：`_evict()` 从最旧往最新扫、跳过在跑的——**在跑的多于上限时，
连刚 `get()` 出来的那条都会被扫到**。所以抢到锁的这一刻必须把手里那个实例
按回 `_items`。测试里那条 `pins_the_instance_back` 就是这么来的
（先造 4 把锁把上限 2 撑爆，再确认没锁的那场真的被扫掉了，前提才成立）。

**`get()` 原来就有一条双读竞态。** 读盘不持锁，两条请求可能同时 miss，
各自 `load_session()` 出一个实例，后写的赢。加了双检之后必须返回**先到的那个**。
这条在加淘汰之前就存在，顺手关掉了。

## 不碰的

单场 `session.messages` 不裁剪——读者当初明确拍板过。那是**单场**的事，
和这次的**跨场**内存泄漏不是同一件事。

孤儿锁的清扫只在超限时做：平时两个字典一一对应（`_try_lock_session` 紧跟在
`STORE.get()` 后面，锁永远是给此刻还在 `_items` 里的 sid 造的），
孤儿只可能由淘汰本身产生，而淘汰只在超限时跑。
