# v0.8.9 — 跨教材：读得到之后，让它留得下、别冒充、别烧钱

> 补跑「需求覆盖」这一维审查（上一轮它因 API 报错挂了，没有结论）。
> 结论是：**实时层真的能用了；深挖那条线越是真的用起来，结果越差。**
> 日期：2026-08-20。

## 审查先证伪了自己三条怀疑（记下来，免得以后重复怀疑）

- **模型知不知道书架上有哪些书** → 知道。`job.shelf` 在后台线程里赋值，
  `build_user_message` 印成 `[工作目录里还有这些教材]`。
- **`book` 字段填什么、填错会怎样** → PROBE_SYSTEM 明写「写它的书名」，
  书架印的就是书名。实测原样抄 / 带书名号 / 合理简称都命中；写文件名或路径落空，
  但**模型写不出来**——书架里根本没给路径。落空是静默 `continue`，降级不是崩。
- **socratic / examples 的意图文案会不会让师傅懒得调工具** → 不会。两次真跑：
  chip=examples 调了 3 次 read_file，chip=socratic 调了 21 次，
  引的每一句、每个行号回原文核对，**零编造**。审查自己写的是「这项我猜错了」。

## D1 · P1 · 真的跨书读了正文，跨教材题反而被判死

`pen/probe.py:619`：

```python
src = excerpt or anchor_source(raw, job.original_path, job.extra_roots)
```

`or` 短路。只要 `need_read` 带了 `book` 并读成功，`excerpt` 非空 →
**当前手册锚点行的正文根本不取**。而 `validate_slots` 要求题面所有反引号词都出现在
source 里。跨教材题天然两边各引一个词，所以这条**专打跨教材**。

复现（当前手册 writeback-fixture，题面引了本册第 9 行的 `shell`）：

```
A) 没读跨书 → source = 当前手册锚点行 → validate_slots (True, '')
   _harvest 收成：1 条
B) 读了跨书 → source = 跨书正文     → (False, 'quote-not-in-source')
   _harvest 收成：一条都没留
```

**读了反而归零。** 而 `probe.py:265-268` 的注释白纸黑字记着这个 bug 修过一次
（「prompt 承诺核对的是『那几行』…反而被判死…拿不到正文时**跳过**这条检查」），
`excerpt or` 在跨书这条新路上原样复活了它。

**改法**：两段拼接，不短路。跨书正文和当前手册锚点行都是合法出处。

## D3 · P2 · 模糊回退绑到当前这本，标签还照抄模型写的名字

`pen/probe.py:551-557`：

```python
hit = shelf.get(want) or next((v for k, v in shelf.items() if want in k or k in want), None)
if hit is None: continue   # 注释写着「忽略而不是回退到当前这本」
label = f"〔出自《{want}》〕\n"
```

`_shelf_paths()` **不排除 current_path**（`shelf_digest` 排除），于是子串匹配会命中自己：

```
book='手册' → …/writeback-fixture.md  ← 就是当前这本
   喂给模型：'〔出自《手册》〕\n9\t- **shell**：所有「命令行解释器」的统称…'
book='手搓' → …/writeback-fixture.md  ← 就是当前这本
book='教材' → …/SWE-Agent通关手册v2.md，但标签写 '〔出自《教材》〕'
```

两条后果：① 模型拿着**自己那本书**的正文写「跨教材」题，出处是伪造的；
② 题面会引用《教材》《手册》这种书架上不存在的书名。
两行之上的注释说的正是「忽略而不是回退到当前这本」——模糊匹配把它违反了。

**改法**：`_shelf_paths` 排除 current_path；模糊匹配要求**唯一命中**（多于一条就放弃，
宁可落空也别猜）；label 用命中那本的**真实 title**，不用模型写的 `want`。

## D2 · P1 · 实时层给跨教材开了门，没配读取预算

同一句话的真跑对照：

| | read_file 次数 | tool 输出字符 | messages 膨胀 | 末轮 prompt_tokens |
| --- | ---: | ---: | --- | ---: |
| 跨书问题 | 21 / 22 | 46,912 | 2,449 → 69,895（**28.5×**） | 27,344 |
| 纯本书内问题 | 0 | 0 | 2,434 → 4,302（1.8×） | 1,841 |

那 46,912 字符全部进 `session.messages` 并落盘，**本会话之后每一轮都重发**。

`probe.py:8-10` 对同一件事写死了闸：「后台任务一旦能自主循环调工具，
**读者看不见它在烧钱**…广度由代码封死」。实时层同样 `MAX_TOOL_ROUNDS=50` +
**零字符预算**，读者同样只看到「在翻手册…」。
读者当初提这个需求时的原话是「不能采用无限制的广度搜索，否则成本太高、会浪费大量
credits」——那条约束当时只落在了 probe 上。

结构性原因：当前手册有 `[邻域]`（4000 字符垫底），另一本只有 5 条标题，
模型只能开窗口硬翻 640KB。对照跑证明这不是模型一般性乱翻——纯本书内问题是 0 次。

**改法：只对「读别的书」计预算，读当前手册不限。**
本职阅读（写回要先 read_file 看原文、翻本册别的 Level）一次都不受影响，
零回归风险；封住的正好是 v0.8.7 新开的那道门。
超预算后 `read_file` 不报错、不中断，返回一句「本轮跨书阅读预算已用完，
用已经读到的内容作答，或告诉读者你只读了哪几段」——**让它收敛，不是让它失败**。

## D4 · 不在本版修，理由和代价都写在这里

**纯跨书的题拿不到 grounding，被系统标成「我凭记忆讲的」。**
`_anchor_ok` 只对当前手册的索引验证，另一本书的行号 60 / 500 / 3000 **全 False**。
于是一条只关于另一本书的题：`grounding="book"` 要合法锚点 → 拿不到 → 只能填 `"open"`。
而 open 一路：`validate_slots` 直接拒 `bridge` 和 `vs_real`——PROBE_SYSTEM 里
**最像跨教材的两条轴**永远拿不到跨书出处；读者点下去还会触发 `open_intent()`，
师傅开口第一句是「这题手册里没有出处，凭记忆讲」——**而那本书就在磁盘上，
系统 10 秒前刚读过它**。

跨教材题只有「一头锚在当前手册」时才活得下来（实测这种能过）。
所以深挖线上的「跨教材」目前只能是**半跨**。

修它要动 `PROBE_SYSTEM` 的输出 schema（anchors 带 `book` 字段）+ 按书加载索引 +
grounding 第三态 + 一条不同的 `open_intent`。改 prompt schema 必须真跑验证，
和本版这五条「读代码就能定对错」的修复不是一个风险量级，混在一起会让本版无法干净回滚。
**列为 v0.9.0 单独做**，不是不做。

## 两路复核（一路熟这块代码、一路全新视角）

**五条修复方向都对**，但复核挖出**两条是我自己修出来的**。两条都已修，都带反证。

### N1 · P2 · 「唯一命中」数的是 key，不是书

`_shelf_paths` 给每本书登记**两个** key：正文 H1（`_digest` 的 title）和 `meta.title`。
两者在 `build_index` 退回 `path.name` 时不同——条件是 **H1 不在第 1 行、且不以「手搓」开头**。

**Obsidian 笔记带 YAML frontmatter 就一定满足这个条件**：`---\n…\n---` 把 H1 推到第 5 行。
而读者的教材就躺在 vault 里——这不是边角料，是第三方教材的**默认形态**。

复现（`Prompt工程手册.md`，带 frontmatter）：

```
_digest title = 'Prompt 工程手册'
meta.title    = 'Prompt工程手册.md'          ← 两个不一样
keys          = ['Prompt 工程手册', 'Prompt工程手册.md']   ← 同一个文件占两个 key

book='Prompt'    cands=2 → 落空     ← v0.8.9 之前是命中的
book='工程手册'   cands=2 → 落空     ← 同上
```

两个 key 指向**同一个文件**，根本不存在歧义，却被判成歧义放弃。
我的修复在最常见的场景下把功能弄坏了。

改法：`cands` 按**目标 Path** 去重再数，不按 key 数。
label 用「第一个指向它的 key」——`_shelf_paths` 先插正文 H1、后插 `meta.title`，
所以那正是书架上印的名字，不会印成 `Prompt工程手册.md`。

判据本身（「两本不同的书都沾边就放弃」）是对的，只是实现拿 key 当了书。

### N2 · macOS 的 `Path.resolve()` 不规范化大小写

APFS 默认大小写不敏感。模型把 `handbook_path` 抄成 `handbook.md` 读到的是**同一个文件**，
但字符串比较判成跨书，白吃预算。改成 `samefile()` 比 inode。
（这条我自查时发现，复核独立确认了同一条，并指出 76f7483 那个已 push 的提交带着它。）

### 复核确认没问题的

- **D1 拼接会不会让引号校验太松** → 不算漏。`excerpt` 是系统本轮**真读到**的正文，
  不是模型编的；这条检查防的是编造，不是防错配。而且 `anchors` 根本不外露给读者
  （`to_chip()` 只送 `{id, kind, text, why}`，全仓无第二个消费者），
  不存在「题面来自 B 书、出处标 A 书」这种读者看得见的错标。
  新增开销实测最坏 **27 ms**，后台线程、零 LLM 调用。
- **D3 会不会误杀合理简称** → 真实登记表上没有，改前会错绑的三个现在全对了。
- **D2 预算行为** → 实测第 6 次停住，超支 1045 字符（≤ MAX_OUTPUT，可接受）；
  停了之后读当前手册照常、再跨书读不再累加。
- **D2 会不会撬开写闸** → 不会。额度用完的分支会把路径记进 `read_ok_paths`，
  但 `read_ok` 的唯一消费者是 `edit_file` 的前置检查，而 `handle_edit_file` 还要过
  `assert_write_target`（目标必须**等于** original_path），跨书路径进不了写闸。
  是个无害的记账瑕疵。
- **lab/ 对照阅读** → 不受影响。`lab/` 在手册里出现 67 次，但该目录**不存在**；
  真有时那些是几十行的骨架文件，24000 够读十来个。
- **路径误判** → 8 类变体（相对、`./`、`..` 绕圈、大小写、反引号包裹、`:12` 行号后缀、
  symlink）全部实测不误判。

### N1 的加固，以及一条差点混进去的假测试

`_shelf_paths` 存的是**未 resolve** 的 `Path(raw)`。两条登记记录指向同一个文件却写法
不同（一条绕 `..`）时，裸 `Path` 比较不相等，又会退回「同一本书被当成两本」。
`cands` 改成按 `resolve()` 后的路径去重。

写这条回归测试时第一版**是假的**：`_read_excerpts` 内部会自己调 `_shelf_paths` 重建，
在外面往返回值里塞记录根本没用上。发现方式是做反证——把实现改回裸 `Path` 去重，
测试**仍然绿**。改成 `monkeypatch.setattr(probe, "_shelf_paths", ...)` 之后反证才变红。

由此对本轮每条新测试都做了一遍突变检查（破坏对应实现 → 它必须红）：

```
✓ 会红  D1 拼接          ✓ 会红  N2 samefile
✓ 会红  D3 排除当前这本    ✓ 会红  D2 预算
✓ 会红  N1 按书去重       ✓ 会红  书架闸同源
```

六条全部会红，没有第二个假阳性。

### R1 · 看不见的书在参与歧义投票（同一个坑的第三次）

验收又报出一条残留：`shelf_digest` 只印 `MAX_FILES=8` 本，`_shelf_paths` **一本不落**。
于是模型**从没见过**的书也在「书名沾边的有几本」这场投票里有一票。

```
书架印出 8 本: ['Prompt 注入攻防', …]
_shelf_paths 多出: ['检索增强笔记', 'Prompt 工程手册']   ← 模型看不见

book='Prompt'  → 候选 2 本（一本可见、一本不可见）→ 放弃
```

模型指的显然是它唯一看得见的那本，却被一本它压根不知道存在的书否决掉。
反方向也有：`book='工程手册'` 会读到一本从没提供给它的书。

**这是本轮同一个坑的第三次**——书架的闸 vs `read_file` 的闸（v0.8.7/v0.8.8）、
两处各拼一遍根（v0.8.8/v0.8.9）、现在是两处各筛一遍书。
所以这次不打补丁，把「选哪几本」整个抽成 `library_scan.pick_books()`，

## 验收通过的四点（第二轮复核）

- **dict 顺序可靠吗** → 可靠。`_shelf_paths` 在**同一次循环迭代**里先插正文 H1、
  后插 `meta.title`，每个 Path 只在自己那一轮被插入。能让 `next()` 取到 `meta.title`
  的输入确实存在（`_digest` 返回 None：文件 >2MB 或读失败），但**受同一个不变量保护**：
  `shelf_digest` 用的是同一个 `_digest`，同样条件下它也跳过这本书——
  **只以 `meta.title` 为 key 的书，必定不在书架上**，模型得凭空猜中一个没见过的文件名。
- **歧义保护还在吗** → 在。《通关手册甲》《通关手册乙》并存时 `book='通关手册'`
  仍然放弃，而全名各自命中。
- **Path 去重安全吗** → 安全。两个 `setdefault` 传的是同一个 `p` 对象
  （实测 `shelf['A'] is shelf['B'] == True`），连 `==` 都不用走。
- **`samefile` 有没有新问题** → 没有。8 类非法 `resolved`（空串、目录、错误消息串、
  不存在的路径、`~` 未展开、`\x00`）全测了，两个异常方向**都不可达**——
  `_is_cross_book` 只在 `report["ok"]` 为真时调用，那意味着文件真实存在且可读。
  手册本身被删时 `samefile` 抛 OSError，回落路径比较两个方向都正确。
  开销 **0.032 ms/次**。

### 由此揪出的最后一条：`_prefer_nearby` 的「近」只分两档不够

实时层的读取根是 `[REPO_ROOT, vault]`——同名的两份拷贝**都**算「近」，
分不出胜负就退到纯 mtime。复现：

```
vault 那份更新（今天的实情）        → 选中 vault ✓
仓库那份更新（刚 git pull 过）      → 选中 repo  ✗ 读者眼前编辑的是 vault 那份
```

今天真实登记表上 vault 那份更新（8-17 vs 8-13）所以碰巧对，**那是运气**。
读者 `git pull` 刷新了仓库那份、vault 那份没动，师傅就照着仓库那份讲——
正是 v0.8.7 立 `_prefer_nearby` 时要避免的那件事。

改成三档：**当前手册自己所在的那个根**（多个根嵌套时取最深的）> 其他读取根 > 不在根内。
三个场景全对，反向也对（当前手册就在仓库根里时，仓库那份才该赢）。
