# v0.10.2 — 孤儿窗口与超时对齐（修同一场对话双份深挖）

> 规划 v0.10.x 时扭出来的**既存** bug，不是这一轮改动引入的。
> 日期：2026-08-20。

## 病症

同一场对话可能**同时跑两个后台深挖**，钱花两份，读者看不见。

## 证据链

`probe_store.ORPHAN_AFTER_SECONDS = 300`。它的用途是「进程被杀时 running
会留在盘上，不清的话 `try_claim` 永远抢不到坑，前端也会对着一个永远不会
完成的幽灵轮询到超时」。

而 `obsidian/src/deeppoll.ts` 自己的注释里记着：

> 跨书探索要两轮调用 + 读一段别的书的正文，**实测一次 351 秒**

**351 > 300。** 于是 `_reap_orphan` 会在真线程还活着的时候把 `running` 清空，
`try_claim` 随即可以再起一个 —— 同一会话两份深挖并行，各花各的钱。

而且失配远不止 51 秒。真实的最坏耗时是：

```
PROBE_TIMEOUT 150 秒
  × (1 + SDK 默认 max_retries=2)     = 450 秒   ← 单次调用
  × explore 最多两次调用              = 900 秒   ← 一次探索
```

300 秒的窗口连一次正常的跨书探索都盖不住。

## 为什么现在修

**一旦把「深挖单次调用超时」放上设置页（v0.10.7），这个偶发 bug 会变成
「你一调大就必撞」。** 所以它必须排在设置页之前。

## 修法：窗口从超时派生，而不是一个常数

```
窗口 = max(300, 本次的 timeout × 3 × 2 + 30)
                            ↑    ↑
                   SDK 重试 3 次  explore 两次调用
```

`SessionLedger` 加一个 `running_timeout` 快照，`try_claim` 那一刻写入。
**老账本没有这个字段（=0）→ 退回常量 → 行为与 v0.10.1 完全一致**，不需要迁移。

## 顺带解决：`GET /deep` 没有请求体，配额数字从哪来

`budget()` / `inbox()` 报的 `max` / `window_max` 一直是读模块常量。设置页把
这两个数变成每请求可配之后，就会出现「执行用 7、界面显示 40」。

同样靠账本快照：`SessionLedger` 加 `max_per_session` / `max_per_window`，
`try_claim` 写入，报表读 `led.max_per_session or config.PROBE_MAX_PER_SESSION`。
**执行用的数和显示的数于是是同一个数**——比让前端在 query string 里再传一遍
强得多（那又是两个来源，正是本仓踩过三次的形状）。

## 不动 `DEEP_POLL_BUDGET_MS`

前端那 480 秒的轮询预算失效模式是**良性的**：题不丢，会在下一轮搭便车下发，
`deeppoll.ts` 自己写了。硬要联动就得把它从常量变成函数，而 `check-poll.mjs`
是按常量 import 的。不值得。

## 不动 `max_retries`

四个 client 都没显式设，用的是 SDK 默认 2。显式改成别的是行为改变，
和 v0.10.x「默认 = 现状」的验收标准冲突，留给以后单独一版。
本版只是把这个数**算进**孤儿窗口里。
