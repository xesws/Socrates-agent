# v0.8.4 — 两路审查修复 + 第一次真跑

> 起了两个审查 agent（后端并发/成本、需求覆盖/前端），加上第一次真调 LLM 的实测。日期：2026-08-20。

## 第一次真跑的结果

`python3 -m pen.tests.live_probe_eval --live --n 2`，真手册、真轨迹、真 LLM：

```
落点：Level 0 / 第三拍 · 出身：真实框架里的 Bash 长什么样
  [bridge·有出处·now·深度4]
  这一拍数出来的失败场景，到 Level 3 是不是就变成了输出截断和超时那两道闸？
     └ 锚 Level 0 L193-230
     └ 锚 Level 3 L6395-6463
     └ why: 用他自己已经翻过的 Level 3 那两道护栏来回指……
```

跨关搭桥、两个不同 Level 的真锚点、`why` 里明确用上了读者的学习轨迹。这是功能达标的直接证据——**不是模拟，是真调用**。

**但真跑也暴露了两个不真跑就发现不了的问题**：

- 单次探索实测 **约 2 分半**（6k token 输入 + 一段 JSON 输出）。而前端轮询预算只有 90 秒——等不到就走了，那次调用的钱白花。已把预算调到 5 分钟、节拍 2.5→3 秒。轮询是本地 HTTP，且此时 `busy` 早已是 false，界面不受影响。
- `PROBE_TIMEOUT = 30.0` 直接 `APITimeoutError`。探索会静默失败，读者永远看不到深题。调到 90 秒（主对话那条是 120）。

另有一个落点产出为空（`no-candidate`），属正常——prompt 明写「一条都想不出就交空数组」。

## 两个 P0

### P0-1 · 游标推到池子最大 seq，`later` 通道整条死掉

```python
cursor = max([q.seq for q in led.pool] + [since]) if out else since   # 错
```

一次探索产 2 条，`MAX_RELEASE_PER_TURN=1` 只放 1 条，游标却被推到 2。下一轮 `since=2`，第 2 条撞上 `q.seq <= since` **永久不可达**。

**这是我自己在 v0.8.1 修「投递幂等性」时引入的**。两个审查独立复现了同一条。真实 HTTP 路由下：读者一路走到 Level 6，那条 `target="Level 6"` 的问题一次都没被投递过。

它直接判了双通道机制 later 半边的死刑——而 prompt 还写着「拿不准就写 later」，等于把模型往死通道上引。

现有测试恰好遮住了它：`test_advancing_the_cursor_stops_redelivery` 用的是单条池子，此时两种 cursor 定义数值相同。补了「投递完整性」不变量：每条 pending 最终要么被投递、要么被 dropped，没有第三种下场。

### P0-2 · `MAX_VISIBLE` 当终身配额，池子永不衰减

`visible_count()` 统计 `shown + clicked`，**只增不减**。抛满 2 条后 `room` 恒为 0，之后每一条 pending 在进 `_ripe` 之前就被 `continue` 掉。连带两个后果：

1. **TTL 永不生效**——`state = "dropped"` 写在 `_ripe` 里，而 `_ripe` 根本走不到。实测 `now_round` 推到 100 轮，pending 纹丝不动。
2. **`PROBE_PENDING_CAP=3` 变成永久闸门**——每轮产 2 放 1，第 3 轮 pending 到 4，从第 4 轮起 `should_probe` 永远返回 `backlog-full`。

净效果：一次会话最多看到 2 条深题，之后功能静默死亡；而在 pending 未满时还在继续探索、产出不可见的问题，**纯烧 credit 零产出**——与「不浪费 credits」直接冲突，也让读者选的「每轮实质回复都探」在第 4 轮就作废。

修法：TTL 判定提到循环顶部无条件执行；服务端只管「每轮放几条」，「同时可见几条」挪到前端 `mergeDeep`。

## P1

| 问题 | 说明 |
| --- | --- |
| 反引号校验拿错语料 | prompt 承诺核对「anchors 那几行」，代码比对的却是读者框选的那一小段。模型照 prompt 给术语加反引号反而被判死——**读者举的第一个例子最可能就这么挂掉**。改成读 anchors 正文；读不到时**跳过**而不是判死 |
| `grounding="open"` 绕过填槽 | 直接 `return True`，等于 open 这条路上只剩「axis 拼写正确」一道检查。而读者选了 open 题不加标注，更没法自己分辨。现在 open 也要 `alt`/`trigger` |
| 书架泄漏 | 实测送出去过 pytest 临时夹具（其中一本还长得像手册，有 Level 0/第三拍），以及同目录的《2026 年 8 月的复盘 / 和 A 公司的合同条款》。改成**只认已登记手册**且路径必须落在 `handbook_allow_roots()` 内，不再扫同目录兄弟——教材在真实 vault 里通常就跟私人笔记同一个文件夹 |
| 深题只活一轮 | `this.dyn = readDynChips(ev)` 整体覆盖。服务端已标 shown、游标已推过，**不会重投**。花一次独立调用挖出来的问题，下一轮就再也点不到 |
| 前面几轮对话没进 prompt | 读者明确说「能看到前面几轮对话的情况」，而 `ProbeJob` 里只有最后一轮。补 `history`，取 `ui_messages` 而非 `messages`（后者含 tool_call 配对和 reasoning_content，token 翻三倍还把注意力拉回代码细节） |
| 失败不退配额 | `release()` 只还坑位，不退 `probe_calls` 和日配额。一次 LLM 都没打就失败（起线程失败、抢不到信号量、书架读盘炸了）也扣钱——失败越多能用的次数越少，方向是反的 |
| `_CHORE` 误杀 | `替换成\|占位\|行号` 三个词连坐，把「为什么 dispatch 不直接替换成 match 语句，代价在哪？」这类正当的 tradeoff 题也杀了。黄金集里没这类样本，所以「零误伤」的结论没覆盖到这一片 |
| 书架 I/O 顶在 `done` 前面 | `shelf_digest` 要扫登记表、逐本读前 400 行，却跑在请求线程上，和「绝不延长这条流」的目标直接相冲。移进后台线程 |

## P2

- **`_atomic_write` 用固定的 `<path>.tmp`**：两个 sidecar 指同一个 `PEN_HOME`（同一 checkout 起两次，或旧进程没死透）会互相 replace 掉对方的临时文件，抛出未捕获的 `FileNotFoundError`。改成带 pid + 随机后缀。`session.py` 是同一个写法，一并修了。
- **`>= 80` vs `> 80`**：注释说「和 `has_substantive` 的判据保持一致」，实际差一个等号，正好 80 字那一轮两边判断相反。
- **prompt 自己的示范题过不了自己的过滤器**：那条 vs_real 示范题 69 字，超过上限 60。真实好例最长 44 字——是示范题写得太长（一条 69 字的芯片按钮也会撑爆芯片区），缩短它而不是放宽过滤器。
- **英文词数与过滤器不一致**：`PROBE_ENGLISH` 写 35 词 ≈ 207 字符 > `MAX_CHARS_LATIN=170`，模型照 prompt 顶格写会被静默丢弃。改成 28 词。
- **`mergeDeep` 零覆盖**：v0.8.2 commit 声称「重复投递不会变成两个按钮」已验证，实际测的是测试脚手架自己的复刻。把 `mergeDeep`/`keepDeep` 搬进 `deeppoll.ts`，`check-poll.mjs` 现在跑真代码（8 → 14 项）。

## 两个审查确认成立的约束

- 探索线程**从不碰 `PenSession`**：对 `save_session`/`STORE.*` 打桩计数 = 0
- 轮询端点**从不取会话锁**：持锁时仍 200
- 探索**永不带 tools**：抓 kwargs 实测「带 tools 的调用 = 0」
- 调用/读取上限封死：喂 5 段 `need_read` 实际只读 2 段；第二次调用再要读被结构性忽略
- LLM 配置在起线程那一刻冻结，跨主机钥匙保护生效

## 仍然没做的

- **跨教材只能停在标题层**：`_read_excerpts` 只读 `job.original_path`，读不到别的教材正文。
- **配额耗尽时零 UI 信号**：`budget` 服务端返回了、`types.ts` 也声明了，前端不显示。
- **读者选的是「每小时 40 次」，实现是「每天 40 次」**，严了 24 倍。真实用量（每天几轮）下够用，但这是个明确的偏差。
- `_footprint` 只用锚点标题，没用轨迹里存着的 `user_text`。
