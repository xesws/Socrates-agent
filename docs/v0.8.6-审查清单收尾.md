# v0.8.6 — 审查清单收尾

> 两路审查报告里剩下的三个小项。日期：2026-08-20。

## 1. system prompt 没有字符预算（真实风险）

`build_user_packet` 从 v0.8.0 起就按 `TOC_CHARS` 收行，而 `build_system` 一直没有——目录和 Q 清单是原样拼进去的。实测：

```
当前手册（13083 行）  → system 5676 tok
同结构的 5 倍厚手册    → system 23390 tok   ← 没有任何上限
```

这本手册够用不代表下一本够用，而且探索是每轮实质回复都跑的。

**截断策略不能砍尾巴。** 这个教训是现成的：`build_user_packet` 原来写 `toc_lines[:80]`，而那本手册有 87 条，砍掉的正好是 Capstone 和附录——跨关问题的必需品，v0.8.0 才刚修过。

改成 `_thin_by_level`：超预算时一轮轮往下削**每关**的条数（12 → 10 → 8 …），保证每关都还有代表，并在末尾注明「每关只列了前 N 条」。验证：8 倍厚的手册封顶后，`Capstone` 和 `附录` 仍在，每个 Level 都还有行。

## 2. `_read_excerpts` 忽略 `end_line`

模型说要读 10–20 行，代码一律读 80 行——它要的「一段」和拿到的不是一回事。现在按 `end_line` 算跨度，仍受 `PROBE_READ_LINES` 封顶。

## 3. `should_probe(ok=...)` 的调用点恒为 True

审查指出 `turn-failed` 分支不可达。这是对的但**不是 bug**：`_maybe_probe` 挂在 `done` 事件上，而出了 `error` 就不会有 `done`。保留这个参数是为了让这个纯函数自己说得清完整的判定条件，也让「失败轮不花钱」这条规则有测试可断言。加了注释说明，不改行为。

## 明确不做的两条

- **`STORE.get()` 在 sidecar 重启后可能给出同一 sid 的两个实例**：审查自己标注了「后果是窗口内的脏读而不是丢数据，不建议现在动」。真正的写者只有一个（`/v1/chat` 持会话锁），`STORE.save` 又会把 `_items` 指回来。
- **跨进程文件锁**：`.tmp` 名字冲突已在 v0.8.4 修掉（带 pid + 随机后缀），剩下的「两个 sidecar 同 PEN_HOME 时后写的赢」需要真正的文件锁。默认单进程本地工具，不为它上锁。
