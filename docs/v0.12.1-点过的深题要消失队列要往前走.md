# v0.12.1 — 点过的深题要消失，队列要往前走

> 读者：「一旦某一个 deep dive question 被问了之后它还不会消失，这肯定不行。
> 问过之后肯定要 update……得把 question queue 下一部分的候选 pop 上来才对。」
> 日期：2026-08-21。

读者看到的是一个症状，底下压着三条，最后一条会让深挖**永久停摆**。

## ① 点过的芯片被 `keepDeep` 捞回来了

点深题走的是 `send("free", d.text)`，服务端 `mark_clicked` 会把它标成
`clicked` —— 这一半是对的。但前端的 `this.dyn` 没动，而收尾时：

```js
this.dyn = [...keepDeep(this.dyn), ...readDynChips(ev)]
```

`keepDeep` 只认 `kind === "deep"`，把刚点过的那条原样留下。于是它一直挂在那儿。

**修**：`send()` 一开始就把正要问的那条深题从 `this.dyn` 里摘掉。读者点下去
的那一刻它就该消失，不用等服务端回话——那是本地就知道的事实。

## ② 重开侧栏时 `clicked` 又被恢复回来

`_public_session` 恢复的是 `state in ("shown", "clicked")`。问过的题于是
关一次面板就复活。改成只恢复 `shown`。

## ③【最严重】队列满了会死锁，深挖永久停摆

`inbox()` 是**唯一**会推进池子状态的地方——投递、标 `shown`、跑 TTL 过期，
全在它一个函数里。而它只有一个调用方：`GET /v1/sessions/{sid}/deep`，
**而那个端点只在 `done.deep_running === true` 时才被前端轮询**。

于是：

```
池子攒够 3 条 pending
  → should_probe 返回 backlog-full（这道闸的本意是「手里还有货就别再探」）
  → 不起探索 → done.deep_running = false
  → 前端不轮询 → inbox 永远不被调
  → 既不投递也不过期 → pending 永远是 3
  → backlog-full 永久成立
```

**深挖从此再也不来，读者一个提示都看不到，只能新开会话。**
实测复现过。

而 `docs/v0.8.1` 的原始设计里本来写了这条：

> `timing=="later"` → 留在池子里，**每轮 chat 的 `done` 重新过一遍闸门**，
> 成熟了搭便车下发，零额外往返。

**这条从来没实现。** 补上它，三个问题一起解：

- 每轮 `done` 都带上池子里成熟的题 → 队列每轮都往前走，不依赖探索跑不跑
- 点过一条之后，下一条当轮就顶上来
- `backlog-full` 不再是死结：`done` 那条路会把货发出去、把过期的清掉

## 不做

- 不动 `MAX_RELEASE_PER_TURN = 1`：一轮蹦两条就成噪音，这是当初定过的。
- 不动 `should_probe` 的 `backlog-full` 闸：它本身没错——手里有货就别再花钱探。
  错的是「唯一的出货口挂在探索跑不跑上」。
